# 計算ロジックと精算ルール

家計簿アプリのコア計算ロジックを「**決定 / 背景 / 式**」の組で記述する。実装の根拠を確認したいときに参照する。実装本体は `app/domain/budget/` および `app/features/budget/`。

---

## 1. 翌月入金額の計算

### 決定

各個人の翌月入金額は、固定基本額から個人の通常財布での立替額を差し引いて求める。

```
個人の翌月入金額 = 固定基本額 −（個人の通常立替支出合計）
```

精算フラグ（`shouldSettle`）が TRUE のレコードのみを対象とする。

特別財布の精算は **この月次入金には合算せず、財布ごとに独立して精算する**（§6 を参照）。旅行などは月をまたぎ、閉じるタイミングも任意のため、月次サイクルから切り離して扱うほうが運用に合う。

### 背景

家族間で月次の現金移動を最小化するため、毎月の入金額を立替額に応じて自動調整する。これにより「個別に精算する」運用を省き、固定スケジュールでの 1 回の入金に集約できる。

---

## 2. 精算フラグのデフォルト値

### 決定

新規取引レコードを登録する際、`shouldSettle` のデフォルトは **常に true** とする（実装: `app/features/ledger/register.ts`）。

### 背景

家族の共有家計簿という用途上、**ほぼすべての取引が精算対象** になる。「精算しない取引（プレゼントを贈ったときの個人負担など）」は例外であり、その都度フラグを倒す運用としたほうがミスが少ない。

明示的に精算対象外にしたい場合は、スプレッドシート上で当該レコードのフラグを後から FALSE に書き換える。

---

## 3. アクター列の既定と立替の表現

### 決定

LINE（AI 解析）経由で元帳に書き込むアクター列は、既定で `共同` とする（実装: `app/features/ledger/register.ts`）。AI に「立替か共同か」を判断させない。

個人が立替えた取引は、その行の `actor` をスプレッドシート上で **個人名に手動編集** して表現する。精算ロジックは `actor` 列を読み、ユーザー名と一致する支出を「その人の立替」、それ以外（`共同` など）を「共同口座払い」として扱う（実装: `dashboard.ts` の月次精算、`special-wallet.ts` の特別財布精算、`getSavingsData.ts` の推定残高）。

### 背景

入力時点では大半が共同支出なので既定を `共同` にしてミスを減らし、例外である立替だけを手動で個人名に倒す。立替判定を `actor` 列の一層に集約することで、別管理シートを持たずに済み、ダッシュボード集計のクエリも単純に保てる。

詳細は `./data-model.md` の元帳セクションを参照。

---

## 4. 折半の端数処理

### 決定

折半で 1 円未満の端数が発生する場合、**ユーザー配列の最後のユーザーが端数を負担** する（通常財布・特別財布で共通。実装: `app/features/budget/dashboard.ts` および `app/features/budget/special-wallet.ts`）。

### 背景

決済日時の月偶奇でローテーションする案も検討したが、負担者が決済ごとに変わると精算結果の説明が難しくなる。「最後のユーザーが端数を負担」は実装が単純で、月次・特別の両方で同じ規則に統一できる。1 円の偏りは長期でも実害が小さいため、単純さを優先する。

---

## 5. 赤黒処理（キャンセル）

### 決定

キャンセルが発生した場合、過去レコードを修正せず **マイナス金額の新規レコードを追加** する。

### 背景

スプレッドシートを直接編集する運用上、過去レコードの修正は変更履歴を辿りにくく、集計途中のスナップショットと整合が取れなくなる。キャンセルを赤黒で表現することで、元帳は append-only に保たれる。

---

## 6. 特別財布の精算

### 決定

特別財布は **財布ごとに独立して精算** する（実装: `app/features/budget/special-wallet.ts` の `computeWalletSettlement`）。最初に原資を入金するとは限らず、旅行などでは個人が立替え、財布を閉じた後に精算するケースが多いことを前提とする。

精算対象は当該財布の `shouldSettle=TRUE` の支出のみ。負担割合は **折半固定**（端数は §4 のとおり最後のユーザーが負担）。

立替者は元帳の `actor` 列で判別する（§3 を参照）。`actor` がユーザー名の支出はその人の **立替**、`共同` などユーザー名でない支出は **共同口座払い**（後から入金指示で賄う原資）として扱う。

```
S      = 総支出（shouldSettle=TRUE）
Pᵢ     = actor=個人i の支出合計（立替）
S_pool = S − ΣPᵢ          共同口座払い（actor がユーザー名でない支出）
Bᵢ     = S を折半（端数は最後のユーザー）
netᵢ   = Bᵢ − Pᵢ          恒等式: Σnetᵢ = S_pool
```

精算判定（2 人）:

1. **両者とも `netᵢ ≥ 0`** → 各人 `netᵢ` を共同口座へ **入金指示**。入金合計は `S_pool` に一致する。個人間送金は発生しない。
2. **片方が `netᵢ < 0`（立替超過）** → その人が `|netᵢ|` を **受取**。相手は `S_pool` を共同口座へ **入金指示** し、加えて `|netᵢ|` を **個人間送金** する。

旅行で全額を立替えた（`S_pool = 0`）場合は、自然に純粋な個人間送金へ収束する。

精算が済んだら、ユーザーが財布マスタの `settled` を手動で TRUE にする（精算のやりとりが終わってからトグルする完了マーカー）。精算後に支出が追加されたら `settled` を FALSE に戻す。

プロダクトは 2 人前提のため、ユーザーが 2 人でない・総支出が 0 の場合は精算なしを返す。

### 背景

月次入金へ合算せず財布単位にするのは、特別財布が月をまたぎ閉じるタイミングが任意で、月次サイクルに乗せると「どの月に計上するか」が曖昧になるため。共同口座への入金指示を基本としつつ、立替が共同口座払いを上回るときだけ個人間送金へフォールバックすることで、月次財布と同じ「立替を入金で相殺する」ロジックを保ったまま、立替超過のケースも閉じられる。
